### A second declared run, 64 KiB against 512 KiB on the host's network: the plan, written before the run

The first declared run above missed its margin on the uncompressed page, and that result stands as recorded: nothing here removes it or reads it again. Its second review left two ways on, to close this or "to run again under a protocol that can tell 1% on that workload", and the maintainer asked for the second: a protocol first shown to tell 1% by comparing a setting with itself, then a new declared run under it. This is that plan. The margins are the first plan's, +1% with no floor on a workload held as fast as it was, and 5% as the smallest worthwhile reduction.

What was looked at before this plan, and changed nothing in the first run's reading: one setting (64 KiB) on the uncompressed 9,793-byte page on a c-16 (Xeon Platinum 8280, Linux 6.8.0-149), 30 turns a mode, card-market's image built from main `14126d2a8`. Its cycles a request varied from turn to turn with a standard deviation of 3.99% of the mean behind a published port with a fresh start each turn (as the first run measured), 2.51% behind a published port in one start, 1.56% on the host's network with a fresh start each turn and 0.91% on the host's network in one start; user instructions a request were between 76,922 and 76,972 in every turn of all four. So most of what the first protocol could not tell apart came from the published port (Docker's proxy and bridge between `wrk` and the app), and the rest from the start.

1. The protocol is the first plan's with one change: the app runs on the host's network (`--network host`), not behind a published port. As before: the app pinned to one CPU with one runtime, `wrk -t2 -c64` on two other CPUs, `perf stat -e cycles:u,cycles:k,instructions:u` on the server process from a fourth; each turn a freshly started container, 2 s of warm-up, then a 3 s run inside a 3.4 s count; the settings' order turned every pair; a pair with a failed request or a counter under 100% is reported. One image on each host, card-market's built there from `faba240cd` (this branch with main `14126d2a8` merged), with only `MALLOC_CONF` changed between the two sides, so both sides are one binary and no floor is asked for.
2. No regression, held to +1%, 200 recorded pairs after one that is not, each: the 9,793-byte item page with `identity`, with `gzip, deflate, br, zstd` and with `br`. The bound is the order statistic, the 113th of the 200 sorted per-pair changes in user plus kernel cycles a request.
3. What the run can resolve: before each of those three, on the same host, 64 KiB against 64 KiB (one setting under two labels) on the same workload, 200 recorded pairs after one that is not, read twice from the same pairs: as recorded, and with the labels swapped. If either reading's bound is at or above +1%, that workload is not resolved, and not resolved does not pass whatever its comparison's bound.
4. Reduction claimed, each with a smallest worthwhile reduction of 5%, claimed only if the bound is at or below -5%, 40 recorded pairs after one that is not (the 26th of 40): the item page made 32,501 bytes long with `br`, that page at 202,041 bytes with `br` and at 495,521 bytes with `br`. The lengths are the first run's fixtures on the first run's commit; the run records what they are on this one.
5. Three c-16 hosts, each given one no-regression workload and one long page before anything is measured: `identity` and the 32,501-byte page; `gzip, deflate, br, zstd` and the 202,041-byte page; `br` and the 495,521-byte page. On each host the order is the self-comparison, the comparison, the long page. Every comparison runs whatever the one before it showed; none is run again, and no pair is dropped for its result.
6. The two settings' answers are compared byte for byte but `Date` and `ETag` before each comparison, and a comparison whose answers differ otherwise is not counted.
7. A margin not met, a workload not resolved, or a reduction not established is reported as that. The change goes ahead on cycles only if all three margins are met with their workloads resolved; a reduction that is not established is not claimed.

Not planned: 512 KiB against 1 MiB; a client with gzip alone; pages past 496 KB; more than one runtime; another host kind.
